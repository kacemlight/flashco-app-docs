# 2. Blueprint Notation

FlashCo's core design bet: **multi-agent behavior should be data, not
code.** A blueprint is a complete, versioned specification of an AI team —
who the agents are, what they may touch, how they collaborate, and what
they do first — expressed as reviewable documents rather than scattered
prompts and hardcoded orchestration.

When behavior is data you can diff it, fork it, rate it, sell it, and ship
a behavioral fix by editing a document. That single decision is what makes
a blueprint *marketplace* possible.

## The five artifacts

A blueprint compiles to five artifacts, rendered per launch:

### `SOUL.md` — why the company exists

The constitution: mission, success criteria, deliverables with a quality
bar, operating principles, and resource constraints. It is injected into
**every** agent's system prompt, making it the single source of truth for
what the team must accomplish.

```markdown
# Mission
{{mission_brief}}

# Success Criteria
- Every deliverable traces to the mission
- Ship early, iterate — drafts beat silence

# Constraints
Time: {{duration_hours}}h · Budget: {{budget_total}} credits
```

### `AGENTS.md` — how the team collaborates

The org chart as executable prose: per-agent ownership, the workflow order,
handoff quality gates, decision authority, and conflict resolution. It
encodes the **PM-as-dispatcher contract** (see
[doc 3](./03-orchestration-patterns.md)) — and the runtime scheduler is
built to expect teams to behave exactly as this file says. Document and
runtime are two projections of the same design.

### `TOOLS.md` — who may touch what

The capability contract: an **agent × integration matrix** stating which
agent owns which external system, plus *operation playbooks* — numbered,
ordered flows for each integration ("1. list models → 2. locate the parent
folder → 3. create the fragment → 4. populate fields → 5. publish and poll
the job"). Never vague "use tools when appropriate" filler.

Critically, this document is **generated from the same data that drives
runtime enforcement** (the per-agent tool allowlists), so what agents are
told and what the sandbox permits cannot drift apart.

### `HEARTBEAT.md` — the reporting rhythm

Check-in cadence, progress format, budget alert thresholds, and escalation
triggers. It drives scheduled morning/evening briefings from the PM — the
company reports to its investor like a real team, unprompted.

### `tasks.json` — the initial plan

The seed task graph. Each task has a title, an assigned role, a priority,
and `depends_on` edges pointing at earlier tasks. Generated by an LLM
through a **schema-forced tool call** — the API validates the structure, so
a malformed plan is impossible rather than merely handled.

## The template layer: placeholders

Blueprints are templates, not instances. `{{mission_brief}}`,
`{{budget_total}}`, `{{deliverables_list}}` and friends render at launch
against the investor's actual mission. Two extra mechanisms:

- **AI-derived placeholders** — a cheap model extracts structured fields
  (sector, target market, competitors, key questions) from the free-text
  mission brief at launch, so blueprint authors can reference
  `{{competitors}}` without asking the user to fill a form.
- **Custom placeholders become forms.** Any unknown `{{token}}` a creator
  writes into a workspace file is auto-detected and becomes a typed input
  field in the launch flow. The blueprint's UI is generated from its
  documents.

## Per-agent capability gating

Each agent in a blueprint carries two allowlists, configured visually in
the wizard:

- `allowed_integrations` — which connected systems this agent may use
  (empty = all; a sentinel value expresses "none").
- `allowed_tools` — individual tool names within those integrations
  (checkbox-level granularity).

The same lists serve three purposes at once: they generate the TOOLS.md
matrix, they drive the runtime's three-layer tool filter
([doc 5](./05-security-model.md)), and they show investors exactly what
they are authorizing before launch. One source of truth, three
projections.

## The generation pipeline

Creators don't write these documents by hand (though they can edit
everything). The wizard generates them with model calls that are given
unusual context:

- The **integration registry's capability descriptions** — human-level
  operation lists per integration — so TOOLS.md contains concrete
  playbooks even for integrations whose tool names are only discovered at
  runtime (see [doc 7](./07-integration-layer-mcp.md) for why enumerating
  those names would invite hallucination).
- The **agent-integration ownership matrix**, computed from the gating
  lists, marked *authoritative* in the prompt: the model may not add,
  remove, or reassign ownership.
- A **quality bar with contrastive examples** — the prompt includes a BAD
  (vague, passive) and a GOOD (concrete, imperative, ordered) sample and
  requires every playbook to read like the GOOD one.
- Structured outputs (`tasks.json`, extracted placeholders) are produced
  via forced tool calls with JSON schemas, never free-text-then-parse.

## Lifecycle of a blueprint

```
create (wizard) → save draft → publish (community / premium / private)
      ▲                                        │
      └── fork ◀── marketplace ◀── launch ◀────┘
                        ▲
                        └── retrospective scores (doc 6) feed back
```

Blueprints are forkable like repositories and rated two ways: user reviews
and **retrospective scores** — the LLM-judge evaluation of every company
launched from them. Over time the marketplace surfaces designs that
*measurably work*, not designs that market well. Premium blueprints carry a
price with a creator revenue share, making good agent-team design an
economy of its own.

## Why documents and not a DSL

A YAML/JSON orchestration DSL was the obvious alternative. Documents won
for three reasons:

1. **The artifact is the prompt.** Whatever notation you pick must
   ultimately be rendered into model context; markdown-with-structure *is*
   that rendering, with no lossy translation layer.
2. **Creators are not programmers.** The wizard's users design teams in
   natural language; a DSL would gate the marketplace to developers.
3. **Review culture.** Documents get read, diffed, and critiqued the way
   config files never are — and behavioral drift in a system this
   autonomous is exactly what needs human review.

The structured parts that *must* be machine-precise (task graphs, gating
lists, input schemas) are JSON with schema validation. Prose where humans
decide; schemas where machines depend on it.
